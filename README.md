# aimovice

**本地运行的 AI 自动化解说视频平台**。输入一个选题,自动产出可直接发布的 9:16 竖屏成片。

```
选题 → 事实采集 → 解说脚本 → 分镜设计 → [人工门禁 A]
    → 素材检索 → 提示词编译 → 草稿生成 → [人工门禁 B]
    → 成片生成 → 质检 → 配音混音 → 字幕封装 → 成片导出
```

### 3. 启动

```bash
python run.py            # http://127.0.0.1:8848
python run.py --port 9000
```

**长时间运行请用脱离托管的启动方式:**

```bash
powershell -ExecutionPolicy Bypass -File scripts\serve.ps1 -Port 8848
```

直接 `python run.py` 时,进程是托管后台任务的子进程,而托管任务有 1 小时上限,
到点会把服务一起收走 —— 表现是"服务莫名其妙没了",实际只是超时,日志里
没有任何异常堆栈。`serve.ps1` 用 `Start-Process` 起独立进程,不受此限制,
并把输出写到 `data/logs/server-*.log`。

> `serve.ps1` 刻意只用 ASCII:Windows PowerShell 5.1 在没有 UTF-8 BOM 时
> 按 ANSI 读取 `.ps1`,中文注释会变成乱码并直接把脚本解析搞挂。

打开浏览器,首页会显示环境自检结果:ffmpeg、生成通道、LLM 三项全绿才可完整跑通。

### 4. 跑第一条视频

1. 首页填「选题」(如 `比亚迪汉 EV 2026 款`)→ 时长 60 秒 → 创建。
2. 系统自动跑完**事实采集 → 脚本 → 分镜**,停在**门禁 A**。
   这几步只消耗检索与文本调用,不消耗视频额度。
3. 在工作台检查事实来源、脚本、分镜表,可直接编辑。
4. 点「确认脚本与分镜」→ 开始**草稿生成**(Hailuo-2.3,约 1 分钟/镜头)。
5. 逐镜头看草稿,不满意就点「重拍」。全部通过后停在**门禁 B**。
6. 点「草稿通过,开始成片生成」→ H3 出片(15–30 分钟/镜头)。
7. 自动完成质检、配音、字幕、合成,产出 `output.mp4` 与 `cover.jpg`。

## 核心设计

### 为什么旁白走独立 TTS,而不是 H3 原生音频

H3 的卖点是画面与声音一次生成。但解说视频的旁白必须**逐字准确** —— 车型名、
"702 公里"、"3.8 秒"由视频模型朗读时发音错误率不可控,也无法逐句调语速与停顿。

因此默认架构:**H3 出画面 + 环境音(无人声)+ 独立 TTS 旁白轨 + BGM**,剪辑阶段混音。
`narration_mode=native` 可切回 H3 原生对白。

### 为什么需要两道人���门禁

H3 单任务要 15–30 分钟、消耗套餐额度。在错误分镜上返工 20 个镜头是真实会发生的灾难。
所以:

- **门禁 A**:确认脚本与分镜后,才允许进入任何生成阶段。
- **门禁 B**:确认草稿通过,才允许进入成片阶段(H3)。

草稿档用 Hailuo-2.3,约 1 分钟出片,是快速迭代的主战场。
**宁可多花 3 分钟审草稿,也不要让 20 个镜头在成片档返工。**

### 长视频一致性(60 秒以上最关键)

10–30 个镜头各自独立生成时,最容易崩的是跨镜头跳变:同一辆车颜色变了、
上一镜停在展台下一镜到了街头。双层机制解决:

1. **全片共享一套参考图集**(≤5 张,来自联网检索的真实实拍图)→ 锁车身颜色与内饰。
2. **镜头 N 的尾帧作为镜头 N+1 的首帧**(ffmpeg 抽帧 + I2VA 前置对齐行)→ 锁场景连续性。

由此产生调度约束:镜头间有数据依赖,必须**按链编排** —— 每链 3 个镜头,
链内串行、链间并行。实际并行度 = 链数,而非镜头数。

尾帧抽取失败会降级为"仅共享参考图集",标记 `consistency=degraded` 并在界面明示,不阻断流水线。

### 墙钟时间为什么不是线性的

链内串行意味着**一条链的 3 个镜头必须依次跑完才释放下一条链**,所以并行度上限是
链数,不是镜头数。总时长 = 波次 × 链长 × 单镜头耗时:

| 时长 | 镜头 | 链 | 波次 | 草稿档 | 成片档(上界) |
|---|---|---|---|---|---|
| 60s | 10 | 4 | 1 | 3 min | 45–90 min |
| 90s | 15 | 5 | 1 | 3 min | 45–90 min |
| 120s | 20 | 7 | 1 | 3 min | 45–90 min |
| 180s | 30 | 10 | 2 | 6 min | 90–180 min |
| 240s | 40 | 14 | 2 | 6 min | 90–180 min |

**240 秒与 180 秒的等待时间相同** —— 波次在 40 镜头内没有再跳档,多出的 10 个
镜头只多花等效用量,不增加墙钟。这就是把时长上限定在 240 秒的原因;再往上
(300s = 17 链 = 3 波次)就会跳到 135–270 分钟。

这是**上界**:末波往往是不满链。宁可高估,也不要让人低估等待时间后误判成卡死。

### 提示词编译器

H3 有严格的提示词格式(`integrated_multimodal_description` / `overall_soundscape` /
`non_diegetic_music` 三字段,`[Shot N]` 标签与时间戳规范,总长 ≤7000 码点)。

编译器把职责拆成三层,让**格式正确性从概率问题变成确定性问题**:

```
translate_shot()   需要 LLM:中文分镜 → 结构化英文
        ↓
assemble()         纯函数:按官方格式拼装(可单测)
        ↓
validate()         纯函数:8 条硬校验,不合规就拦下,绝不发给模型烧额度
```

不让 LLM 直接写最终提示词,是因为模型的自由发挥会把时间戳写成 `03:5`、
把风格描述塞进 `[Shot 1]` 前面、把英文字段里混进中文 —— 这些都会被 H3 静默劣化。

### 参考图素材来源链

参考图决定全片是不是同一台车、是不是**这台**车。来源按可靠度排序,逐级降级:

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | **用户手动上传** | 放进项目的 `user_refs/` 目录(`.jpg/.png/.webp`)。唯一能"保证是这台车"的来源,永远排在自动检索之前 |
| 2 | `matrix.search_images` | 联网图片检索。**可用**,但 payload 形状必须对(见下) |
| 3 | **维基共享资源 / 维基百科** | 免密钥、免注册。`2020 BYD Han EV front.jpg` 这类真实量产车照片,多为 CC BY-SA,自动记录授权与作者 |
| 4 | AI 生图兜底 | 模型**编**出来的虚构车型。报告会写 `has_real_photo: false` 与 `warning` |

`refs_report.json` 里会记录来源链走过的每一步、来源构成 `origin_counts`、
是否拿到真实照片 `has_real_photo`、被硬过滤掉多少张 `rejected_by_filter` 及原因,
以及校验结论 `verify_parsed`。

几条实测结论(写代码前先踩过):

- ⚠️ **`search_images` 曾经"整体不可用"是误判**。工具一直是好的,坏的是本地
  payload:发的是 `{"queries": ["关键词"]}`(字符串数组),而 schema 要求对象数组
  且每项必含 `query` / `prompt`(相关性过滤)/ `task_name`。正确形状:

  ```python
  {"queries": [{"query": "比亚迪汉 实拍 45度前侧 整车",
                "prompt": "real photograph of BYD Han EV (electric car), exterior "
                          "three-quarter front view, professional editorial photo, no "
                          "diagrams, no e-commerce listings",
                "task_name": "auto"}]}
  ```

  `prompt` 是必填的**相关性过滤器**,写得越具体,返回的越像编辑部级车照。
  `CategoryProfile.reference_prompt()` 负责生成它,和 `reference_query()` 分工:
  前者决定"要什么样的图",后者决定"搜什么"。

  **判断一个工具是否可用,拿真实调用结果说话,别从一份畸形 payload 反推。**
- **返回结构是"每个查询一个对象"的数组**(`[{query, images:[…]}, …]`),
  不是顶层 dict 里挂 `images`。只按后一种形态解析会让每条查询的 10 张图全被
  跳过,报告里表现为 `searched: 0` —— 又一次"工具坏了"的假象。
- **`link` 是文章页地址,不是图片地址**。拿它当兜底等于把一个 HTML 页面 URL
  交给 H3 当参考图。图片只认 `image_url` / `url`。
- **检索结果必须筛**。电商白底图(不是这台车)和图库水印图是最高频的两类误命中,
  看域名就能剔(`alibaba`/`ebay`/`dhgate`/`shutterstock`/…),不进视觉校验;
  剩下的**逐张**问视觉模型"画面里是不是目标车型、依据是什么"。
  ⚠️ 校验条件过去是**反的**(只在"全是 AI 图"时才校验,理由是"真实照片不用验")——
  真实来源一多这个前提就塌了。**来源多不等于可信度自动成立。**
- **校验解析不出来时一律保留**,不猜。把"解析不了"当成"全不合格"会把素材层
  变成新的失败源,而这一层的第一原则是降级而不是阻断。
- ⚠️ **视觉问答工具拒收外部直链**,实测返回 `image_info.url could not be used as a
  media source; download ... then call upload_temp_url`。所以外部检索图必须先落地
  再上传才能校验;落地失败的图保留但不参与校验。AI 兜底图例外 —— 它的 URL 本来
  就是临时地址。
- ⚠️ **视觉问答工具恒返回散文描述,不认 JSON;一次给多张图只描述第一张**。
  过去 10 张图一次提交,回来一段只讲第 1 张的散文,解析失败全部保留 —— 校验
  实际是"走过场",汉 EV 的参考图集里混着海豹 07 和飞凡 F7。现在的做法:
  1. 每张图单独问一次(4 路并发),提示词要求说出品牌、车型和依据(车标/车尾字样);
  2. 散文合在**一次** LLM 调用里转成结构化判定,规则是只认描述里明确写出的车型 ——
     没点名就是 `unknown`,不剔;
  3. 视觉模型偶尔会直接给 JSON,但它的标准比这里严得多(实测把"汉 DM"判成不是"汉 EV 2026",
     一次剔掉 8/10),所以先**去掉它自己的 JSON 结论**再交给 LLM,只认它对车标、字样的描述;
     只有一段 JSON、没有描述的回答没有依据,保留。没有 LLM 或调用失败时才退回它的 JSON。
  `refs_report.json` 里的 `verify_sources` 记录每张图的结论来源(`json` / `llm` / `none`),
  `rejected_reasons` 附带 LLM 引用的原话,误判时能直接看出是哪句话导致的。
  实测汉 EV 2026:10 张全部得出结论,剔除海豹 07 ×2、飞凡 F7 ×1。
- **维基会限流**。它有明确的 robot policy,连续请求几次就会 403
  (`Please respect our robot policy`)。因此查询结果落 24 小时磁盘缓存
  (`data/_cache/webassets/`),同一车型重复跑素材层不再打扰对方。
- **本地下载 403 不影响生成**。参考图是以 URL 交给 H3 的,由生成侧自己去取,
  不走本机 IP。下载只为了 Web 预览和抽帧,失败会记进 `download_warnings`。
- **Commons 检索必须过滤**。全文检索对 "EV" 这类缩写极不友好,会混进销量图表
  甚至生物图;文件名含 `diagram`/`chart`/`sales share` 的一律丢弃。
- **不能用中文主体派生英文查询**。`比亚迪汉 EV` 去掉汉字后只剩 `EV`,拿它去搜
  出来全是噪音。实测中文查询本身就能命中英文文件名的真实照片。

### 两种接口后端:mcode 与 direct

所有外部能力都经过 `providers/cli.call(工具名, 参数)`。`CONNECTOR_BACKEND` 决定它落到哪:

- **`mcode`**:`mcode-tools` CLI。登录由 MiniMax Code 应用托管(shared-broker),
  离开 MiniMax Code 就调不通。
- **`direct`**:`providers/direct.py` 用 M Plan 订阅 Key 直连开放平台,按工具名翻译成 HTTP 调用、
  返回与 Connector 相同的形状,上层代码不感知。额度与 MiniMax Code 里用的是同一份。

| 能力 | direct 实现 | 备注 |
|---|---|---|
| 视频 | H3 / H3-Max → `/v2/video_generation`;Hailuo → `/v1/video_generation` | V2 首尾帧与参考图**互斥**:有首帧时丢参考图 |
| 配音 / BGM / 生图 / 音色 | `/v1/t2a_v2`、`/v1/music_generation`、`/v1/image_generation`、`/v1/get_voice` | 模型由 `TTS_MODEL` / `MUSIC_MODEL` / `IMAGE_MODEL` 指定 |
| 图片理解 | `/v1/coding_plan/vlm` | 本地图转 data URI,不需要图床 |
| 视频质检 | 抽帧拼图 → 图片理解 | 开放平台没有视频理解接口 |
| 图片检索 | Bing 图片 | 开放平台没有图片检索接口 |
| 事实:新闻检索 | `/v1/coding_plan/search`(网络搜索) | 事实的 `source_tool` 记为 `minimax.web_search` |
| 事实:同花顺行情财报 / 企查查 | **不支持** | 该来源记失败,其余照常 |
| 配音逐字核对(语音识别) | **不支持** | 跳过,不阻断 |

`.env` 填 `MINIMAX_PLAN_KEY`,`CONNECTOR_BACKEND` 留空时:有订阅 Key 且找不到 `mcode-tools` 就走 direct。
自检:`python -m tests.verify_direct`(便宜项)/ `--video MiniMax-Hailuo-2.3`(再试一条草稿视频)。

### 数据镜头为什么由代码渲染(数据卡片)

视频模型画不出准确的数字和汉字,而"参数硬数据""对比维度""市场格局"这类镜头恰恰是
一个字都不能错的地方。所以段落在 `auto.yaml` 里声明 `card:` 后,镜头改由
`pipeline/cards.py` 直接渲染,不取材、不编译提示词、不消耗生成额度:

| 版式 | 用在 | 内容 |
|---|---|---|
| `spec` 参数卡 | 参数硬数据、使用成本 | 参数名 + 取值 |
| `compare` 对比卡 | 对比维度 | 两个对象逐维度对照 |
| `timeline` 时间线 | (预留给迭代史 / 品牌史) | 年份 + 事件 |
| `bars` 柱状图 | 市场格局、趋势解读 | 同口径数值横比 |

1. **挑**:分镜 LLM 从事实层挑出要上屏的行,每行挂 `fact_id`;
2. **核**:`cards.ground()` 要求每行数字都出现在它引用的事实原文里,低置信度事实不上屏,
   对不上的整行丢弃;剩余行数不够版式下限时整张卡作废,镜头退回普通画面。
   核对明细写在 `cards.json`;
3. **画**:PIL 逐行出现的关键帧 + ffmpeg 拼成 6 秒镜头,底图是参考图集里第一张真实照片(虚化压暗)。
   内容区避开抖音 / 小红书的顶部栏、右侧互动列与底部字幕区。

卡片在门禁 A 之后渲染一次(`cards/NNN.mp4`),草稿档与成片档共用。卡片不进视觉质检,
也不给后继镜头当首帧(尾帧是图表,模型会照着图表"续拍"),后继按链首处理。

### 画面上的中文占位符为什么会被渲染成鬼画符

分镜里的可见文字是**中文占位符**(`[年款标识]`、`[续航版本标识]`、`[百公里能耗]`),
这对门禁 A 的人读最友好。但它一路走到英文提示词里就会出事:

```
Readable on-screen text includes "[年款标识]"
```

视频模型不会渲染汉字,只会把读不懂的方括号内容画成乱码 —— 实测
`drafts/001.mp4`、`drafts/004.mp4` 就是这样。

它能一路溜过去,是因为校验规则 6 用"英文双引号区"当白名单(为了容纳中文品牌名),
而 `visible_text` 恰好是被双引号包起来的。修法是三层:

| 层 | 做法 |
|---|---|
| 提示词层 | `TRANSLATE_SYSTEM` 规则 6 明确要求把中文占位符改写成英文,并给映射示例(`[年款标识]` → `[MODEL YEAR BADGE]`) |
| 代码层 | `assemble()` 里过一遍 `_englishize_placeholder()`:命中词表就翻译,词表外的中文占位符降级为 `[ON-SCREEN LABEL]`。**兜底而不是报错** —— 校验失败会让镜头永远缺提示词、整个项目卡住 |
| 校验层 | 规则 10:方括号内禁止中文。独立于引号白名单,因为方括号是占位符的唯一载体 |

⚠️ 规则 6 的引号白名单**不能收窄**:`normalise_subject_en()` 拿不到英文名时会退回
中文主体名,`assemble()` 会给它包引号,一刀切禁掉引号中文会让这类镜头全线编译失败。

### 真实素材与生成素材怎么混

原则:**能用真实就用真实**。每个镜头先去网上找素材,整条来源梯子都找不到才回退 AI 生成。
真实镜头有两重收益:画面里是真实的那台车;每个镜头还省下草稿 + 成片两次生成
(成片档 $0.48 等效用量 + 15–30 分钟墙钟)。用途是个人学习、不商用。

#### 取材梯子(命中即停)

| 镜头类型 | 判定 | 来源顺序 |
|---|---|---|
| **车辆镜头** | 画面主体是目标车型(外观 / 内饰 / 尾部 / 细节 / 仪表) | ⓪ 素材池 → ⓪ 官方视频 → ⓪ 官方图片 → ① 平台视频 → ② 维基 / 车媒页 → ③ 网上图片 → ④ AI 生成 |
| **非车镜头** | 氛围、城市、车展人流、行业场景 | ① 平台视频 → ② Pexels / Pixabay / Coverr 视频 → ③ Pexels / Pixabay / Unsplash 图片 → ④ AI 生成 |

#### 素材池(`pipeline/library.py`)

旧做法是"每个镜头现搜现切":在搜到的长视频里按固定起点切 6 秒,切到字幕卡、口播就被质检毙掉,
再换个起点赌一次。素材池把顺序倒过来 —— **先攒、再切、再看、最后挑**:

1. **攒**:按车型自动发现一批源(品牌官方号、宣传片、实拍、静态体验;B站 + YouTube,口播类不要),
   加上手动贴的链接、汽车之家官图。6 分钟以内的源整条下载,更长的在 8%–92% 区间分 8 个 40 秒窗下载;
2. **切**:ffmpeg 场景检测(`scene>0.3`),在**原片自己的剪辑点**切段,不会切在转场中间;
3. **看**:每段抽中间帧问一次视觉模型,LLM 转成标签:视角(车头 / 侧面 / 前 45° / 车尾 / 行驶 /
   航拍 / 座舱 / 中控屏 / 座椅 / 细节 / 人物 / 文字卡)、是不是这台车、海报字幕等问题和一句话描述。
   每个源最多看 60 段,长段优先;
4. **挑**:取材时作为车辆镜头的第一级,按镜头视角从同一文件里拼出撑满 6 秒的连续窗口
   (只接同一大类的好段,细节特写两边都能接),官方源、认出是这台车的、首段更长的排前面。
   用过的时间段不会再给别的镜头。
5. **对题**:每个镜头调一次 LLM,把分镜画面描述和候选的一句话描述(文本对文本)对一遍,
   只排除主体对不上的(要两车同框给了一台、要外观给了内饰);挑中的按**画面干净程度**排序 ——
   干净 → 角标 → 烧录字幕 / 主持人讲解。素材池的段**不再逐镜头做视觉质检**:入池时已经看过,
   再问一次只会添噪声(实测把广告片的局部构图判成 cropped、把"驾驶舱"对"车门内饰"判成不对题)。
6. 池子里有可用视频后,车辆镜头**不再走"平台现搜现切"**:池子判了没有合适的,现搜捡回来的是
   猎奇、吐槽类视频。往下走官图 / 网图 / AI。

7. **分镜按池子写**:池子已经有可用视频时,写分镜的 LLM 会先拿到一份素材清单
   (`library.catalog()`:能撑满一个镜头的窗口 + 官图,干净的在前,单一视角不超过四分之一)。
   旁白能被池子里的画面撑住的镜头直接点名素材(`ShotSpec.pool_id`),画面描述**就是素材自己的描述**,
   门禁 A 看到的就是成片里会出现的画面;池子撑不住的(两车同框、特定人物、没拍到的部件)才写给 AI。
   取材时点名的素材排第一,失效了(重新打标签判不可用、文件没了、窗口被占)再按画面描述挑。
   第一次做的车,池子还在后台建,分镜照旧先写画面。

小米 YU7 实测(8 个非卡片镜头,试跑):旧流程 3 个用上真实素材、质检弃用 64 次;
素材池 + 文本对题后 7 个,弃用 16 次,其中 2 个是官方图;分镜按池子写后 7 个全部用上点名的实拍,
剩下的是"YU7 和 Model Y 并排",池子里没有,交给 AI。

池子按车型存在 `data/library/<车型>/`(`library.json` + 原片 + 帧 + 官图),**跨项目复用**。
构建是增量的、有时长预算(`LIBRARY_BUILD_BUDGET`),超时停在当前进度,下次接着做。
项目走到分镜阶段时自动在后台构建,门禁 A 确认时用池子里已有的,不在确认请求里等下载。

```bash
python -m app.pipeline.library build 小米YU7 --brand 小米      # 手动构建 / 续建
python -m app.pipeline.library add 小米YU7 <链接> [<链接>...]   # 加自动搜不到的好素材(抖音只能走这里)
python -m app.pipeline.library show 小米YU7                      # 统计:源、段、各视角可用数
python -m app.pipeline.library sheet 小米YU7 [--usable]          # 导出联系表,人工过一遍标签
```

| 变量 | 默认 | 说明 |
|---|---|---|
| `USE_LIBRARY` | `1` | 是否启用素材池(后台构建 + 取材第一级) |
| `LIBRARY_BUILD_BUDGET` | `1800` | 一次构建的时长预算(秒),`0` 不限 |

#### 落地方式

- **平台视频只下需要的那几秒**:yt-dlp `download_ranges` 截 [起点, 起点+6s],不下整片;
  起点取在时长的 15%–70% 区间,避开片头 logo / 口播和片尾求三连。
- **同一条视频切给相邻镜头**:长视频按不同起点展开成多个候选,同源连用 = 免费的强一致性。
  一个视频在某个起点下载失败(403 / 地区限制),它的其余起点不再尝试。
- **图片做成推拉动效镜头**(`render.still_to_clip`):前景按"完整放进画幅"缩放,上下用同图模糊铺底,
  避免 9:16 裁掉车头车尾;动效在推近 / 右移 / 拉远 / 左移之间轮换。
- **横屏视频同样不裁车**:平台视频几乎都是 16:9,居中裁 9:16 只剩三分之一宽、车头车尾全被切掉
  (质检随即弃用,通路空转)。所以 `clips.fetch_clip` 直接排成 1080×1920:完整画面居中、
  上下模糊铺底;竖屏源正好铺满。

#### 接入时机

- **门禁 A 确认后**取材一次,结果存成 `clips.json`(取材计划)+ `clip_report.json`(每镜头来源、
  失败原因)。命中的镜头直接写成草稿档 succeeded,**不再生成草稿**,门禁 B 审到的就是真实素材。
- **门禁 B 每批放行**时把同一份计划应用到成片档,**不重新抓网络**。
- `ShotSpec` 一列没加字段:真实素材是*后验可得性* —— 先找,找到就用,找不到无声回退生成。
- 真实镜头照常编译提示词:门禁 B 不满意某个真实镜头时,"重试"能回退到生成。
- 一致性链**不重排**:前驱若是真实片段,抽出来的尾帧就是真实车尾帧,恰恰是最好的锚点。

#### 质检与降级

车辆镜头抽中点一帧做质检 —— 不是目标车型 / 画面里没有车 / 主体被裁掉 / 画面不清的弃用(退回生成),
带台标的**只记警告不弃用**
(车媒和平台视频几乎每条都带)。非车镜头不查车型。质检链路抖动时一律保留。

质检和参考图校验共用 `vision_verdict`:**每帧单独问一次**视觉模型,散文回答合在一次 LLM
调用里转成判定(只认描述里明确写出的问题,没提到被裁就当完整)。⚠️ 过去这里有两个叠在一起
的问题,质检实际**从没跑过**:抽帧目标目录没建,ffmpeg 每帧都失败、按"抽不出帧就保留"一路
放行;就算抽出来,一次 10 帧也只有第一帧被描述。

车型判定和参考图校验同一套规则:只剔被**明确认出**的别的品牌或车系,认不出车型的保留。
"没有车"是唯一放宽的一条 —— 视觉模型描述主持人口播帧时只讲人,不会说"画面里没有车",
所以描述通篇没提到任何车辆或车辆部件也算没车;误判的代价只是这个镜头退回生成。
实测(目标汉 EV 2026):5 条本地片段全部被拦(Austin Allegro ×2、主持人口播 ×2、测试图 ×1);
反过来拿 10 张真实车照当帧跑,7 张汉全部通过,海豹 07 ×2、飞凡 F7 ×1 被拦。

任何来源失败(网络不通、没配 Key、站点改版、下载被拒)都只是这个镜头降一级,原因写进
`clip_report.json`,项目页"真实素材"卡片可展开查看。检索失败**不会被缓存**(只有成功结果缓存 24 小时),
修好代理后立刻生效。

### 事实可追溯与事实分层

每个数字型陈述必须携带 `fact_refs`,否则被合规 lint 直接拦截。
事实来自同花顺 iFinD(销量/财报/行业指标)与企查查(工商/商标/合规),
每条都带来源工具、查询串与取数日期,并在界面上一目了然。

这解决的是解说视频最容易翻车的地方:模型凭印象编出一个"看起来很像真的"参数。

**事实分三层,不可混用**(`Fact.scope`):

| 层级 | 含义 | 典型内容 |
|------|------|----------|
| `company` | 公司工商与财务 | 注册资本、法定代表人、证券代码 |
| `product` | **产品参数** | 续航、加速、售价、配置、电耗 |
| `industry` | 行业与市场 | 渗透率、销量排行、政策 |

用公司注册地址去讲产品卖点是解说视频的典型翻车方式,因此脚本提示词里有层级禁用规则,
lint 也有一条专门拦截"用公司事实讲产品参数"。

**关于车型参数从哪来**:iFinD 与企查查**都只覆盖公司层面**,问不出车型续航或加速。
产品参数实际来自 `thsifind.search_news` 的新闻语义检索(`ifind.product_news` 来源)。
两点很关键:

1. **产品向查询串要单独一条**。把"续航 售价 配置"和"销量 财报"混在一条查询里,
   检索结果会被整体拉回公司财经新闻,车型参数被挤掉。实测拆分后产品级事实从 2 条升到 19 条。
2. **新闻有时间陷阱**。同一款车上市多年,检索会捞回发布当天的旧文(比如 2020 年的 605 公里),
   而报道日期可能标着几个月前。因此抽取提示词强制时效规则:超过 12 个月的参数必须
   在句中注明年份并降为 `low` 置信度,绝不当作现售配置。

产品级事实少于 3 条时,事实报告会给出 `product_gap` 警告并在界面横幅提示。

### 合规检查

- 品类禁用词(汽车 10 条 / 美妆 23 条 / 数码 9 条 / 家居 9 条)+ 方向级附加禁用词
- 广告法绝对化用语(所有品类共享)
- 引用了不存在的事实 ID
- 品类必需免责声明自动追加
- **禁止贬低竞品**(所有方向生效):段落里点名了竞品/友商/同级,又用了
  「智商税」「劝退」「垃圾」这类贬义词,即拦下。收窄词表是刻意的 ——
  「A 不如 B」是客观比较,在对比内容里完全正常,不能当贬义处理。
- **层级混用规则只在产品向方向生效**。它的触发词表含「电池」「充电」「配置」,
  而这些词在品牌叙事里同样高频 —— "这家车企最早是做电池起家的"会被判成
  "用公司事实讲产品参数",整个品牌方向会被自己的 lint 掐死。因此品牌/市场方向跳过该规则。

## 内容方向库

一条视频只讲一个内容方向。`auto` 品类内置 7 个方向,建项目时选一个:

| 方向 | 讲什么 | 需要的事实层级 |
|---|---|---|
| `overview` 通用车型概览 | 标准车型介绍(默认) | product |
| `iteration` 车型迭代史 | 历代车型、改款、换代演进线 | product + industry |
| `compare` 横向对比与购车决策 | 同级横比、按人群给取舍建议 | product |
| `tech` 技术与设计拆解 | 三电 / 平台 / 智驾 / 底盘,技术落到体验 | product |
| `cost` 优势、缺点与真实使用成本 | 敢讲缺点,摊开能耗保险保养折旧 | product |
| `brand` 品牌历史与产品战略 | 车企怎么起来的、现在往哪走 | company + industry |
| `market` 汽车市场观察与热点解析 | 份额、格局、热点事件与趋势 | industry + company |

为什么不做成"一条视频覆盖全部 6 个方向":60 秒只有 10 个镜头,6 个维度平摊后
每个不到 2 镜,内容必然稀薄。选一个方向做深,才有可能说清楚。

### 方向决定的不只是段落

- **段落结构**:每个方向用一份 `blocks` 权重表声明"有哪些段落、各占多重篇幅"。
- **事实来源**:每个方向配自己的检索串(迭代史要跨 4 年的改款通稿,市场观察要份额排名,
  真实成本要保险保养)。走一份平铺的来源列表,会让每个方向都拿回一堆用不上的公司财经新闻,
  反把该方向真正需要的挤掉。
- **脚本规则**:`iteration` 要求参数必须带年份,`cost` 要求缺点讲具体且不得贬低竞品,
  `brand` 允许公司事实作主体而禁止用产品参数论证战略。
- **事实缺口告警**:按方向所需层级判定 —— 品牌方向 product 少于 3 条完全正常,不报警。

### 段落结构为什么是"权重铺展"而不是手写

7 方向 × 5 时长 = 35 条例 plan,手写必错。因此每个方向只写一份权重表,
`plan_for()` 用确定性算法按目标镜头数铺展:

```
base_i = max(1, floor(n * w_i / Σw))
多了 → 优先从"允许补位且仍 >1"的块里减
少了 → 按小数部分从大到小补,同分按声明顺序
```

纯函数、无随机、可单测,任意时长都能得到结构正确的序列。铺展结果在
`_validate()` 里对**每个方向 × 每个时长**逐组合校验,配置写错在加载期就炸。

### 铺垫段落要关掉补位

块上可以写 `remainder: false`。最大余数法的标准做法是把余量派给
"权重小 → 小数部分大"的块,而开场钩子权重恒为 1,永远排在补位首位 ——
实测 60 秒下 7 个方向有 6 个拿到 **2 个钩子,12 秒悬念开场把正片挤掉了**。
钩子这类铺垫段落取 floor 就够,补位名额应该留给内容块:

| | 改之前(60s) | 改之后(60s) | 改之后(240s) |
|---|---|---|---|
| iteration / compare / tech / cost / brand / market | hook = 2/10 | **hook = 1/10** | hook = 2–3/40 |
| overview | hook = 1/10 | hook = 1/10 | hook = 4/40(比例本就如此) |

`overview` 不受影响,因为它的权重和正好是 10,整除、不需要补位。

### 改完 YAML 必须重启服务

`load_profile` 带 `@lru_cache`,改 `auto.yaml` 不重启不会生效(测试里需先
`load_profile.cache_clear()`)。

检索侧的参数同理:`images.search()` 没有进程内缓存,但 `webassets` 的维基查询有
24 小时磁盘缓存,改检索串之后若命中旧缓存要等它过期或删 `data/_cache/webassets/`。

### 门禁 B 分批审片

长视频审 40 条草稿不现实,所以门禁 B **按一致性链分批审**(默认每批 4 条链 = 12 镜头):

1. 审完一批 → 点"批准本批",只有这批镜头进入成片档(只为新增批准的镜头编译提示词,
   不重复烧额度)。
2. 本批成片完成 → 回到门禁 B,提示第 k/m 批。
3. 全部批次审完 → 完整性校验(每个镜头都必须有成片)→ 合成。

批次边界必须对齐链边界 —— 把一条链劈成两半,后半段就拿不到前驱尾帧,连续性直接断掉。

配套的完整性护栏:`finish()` 过去只要有任一镜头成功就开渲,会**静默产出缺镜头的短片**。
现在缺镜头会明确报错并列出缺失序号。

## 已知限制

### 模型能力:实测与文档不一致的地方(重要)

以下结论来自**真实提交验证**,不是照抄 schema。schema 上写着支持、实际调不通的,
必须以实测为准 —— 否则每个镜头都会白等一次失败,而且报错完全看不出是哪个参数的问题。

| 模型 | 参考图 | 首帧图生视频 | 画幅 | 尾帧 | 原生音频 |
|------|--------|--------------|------|------|----------|
| MiniMax-H3 | ✅ 1–9 张 | ✅ | ✅ | ✅ | ✅ |
| MiniMax-H3-Max | ❌ | ✅ | ✅ | ✅ | ✅ |
| MiniMax-Hailuo-2.3 | ❌ | ❌ **实测不通** | ❌ 固定 16:9 | ❌ | ❌ 静音 |

- **Hailuo-2.3 收不了图**:schema 明写支持 `input_image` + `reference_type=first_frame`,
  但实际提交一律返回 `connector_tool_error(latency_ms=0)`;纯文生视频正常。
  因此 `ModelSpec.supports_image_input` 按实测置为 `False`,提交前直接把图丢掉降级为文生。
- **Hailuo-2.3 不支持 `ratio`**:该参数只对 H3 家族生效,文生视频固定 16:9。
  草稿档拿回来的必然是横屏,竖屏由渲染层裁切 —— 这是模型限制,不是配置错误。
- **`search_images` 能拿到真实车照,但不保证是这台车**:过去"整体不可用"是本地
  payload 形状错误导致的误判(见「参考图素材来源链」),修正后可正常返回。
  检索结果会混进同品牌其他车型、旧款或改装车,逐张视觉校验能剔掉被**明确认出**的
  别的车型;认不出车型的图仍然保留。检索失败时原因会写入 `refs_report.json`,
  退化到 AI 生图时写入 `warning`。
  **方向库让这条限制更突出**:`横向对比` 与 `车型迭代史` 方向需要两台车同框,
  提示词会尝试点名双主体,但参考图未必覆盖第二台车。要真正锁死外观,唯一可靠的做法
  还是把真实照片放进 `data/projects/<项目ID>/user_refs/` 后重跑素材层。

### 提示词为什么必须点名车型

这是"文案讲 A、画面拍 B"这类问题的根因所在。模型倾向于把主语写成泛化名词:

```
✗ [Shot 1] A dark-colored new-energy sedan drives toward the camera...
✓ [Shot 1] A BYD Han EV, a dark-colored electric sedan with its slim full-width
   LED headlight bar illuminated and its sleek fastback silhouette...
```

编译器因此新增了两道机制:

1. `translate_shot` 要求 LLM 额外返回 `subject_en`(品牌+型号的英文罗马化),
   并明确禁止用 "a sedan" 这类泛化名词;
2. `validate` 增加**规则 9**:提示词里找不到主体锚点就直接拦下,绝不发给模型烧额度。

`assemble()` 会在第一个节拍开头主动补上主体名(中文品牌名用英文双引号包裹,
以免触发"画面描述不得含中文"的规则)。

### 多主体画面(双车同框)要加在**分镜**上,不是编译上

`竞品对比` / `历代车型` / `改款升级` 这类段落,画面必须出现**第二台车**。
关键在于加在哪一层 —— 加错了地方等于没加:

- 编译器加 `subject_en_secondary`(可选第二锚点):实测 `ready_shots` 之外,
  真实跑下来 5 个多主体镜头里只有 2 个真的有第二台车。
- **根因不在编译器,在分镜**:分镜提示词的 SYSTEM 写着"必须与旁白内容一致",
  模型把**旁白**当成了硬约束,把"节拍方向"当建议。旁白讲"这次改款,底盘是重头戏",
  模型就画底盘特写 —— 节拍要求的"新旧款同框"彻底丢失。编译器拿到的
  `visual_zh` 里压根没有第二台车,自然无从锚点。

所以硬要求必须写进分镜的镜头清单,并在 SYSTEM 里声明不可协商。改后实测
5/5 镜头都出现了第二台车。注意这只是**结构**保证 —— 硬要求能逼模型画出第二台车,
但不一定画成真正可对比的并排构图(实测仍有"另一台旧款车虚化在背景"的情况)。

- 由此推出的结论:**草稿档没有任何图像层面的连续性。** 草稿模型既不吃参考图集,
  也接不了链内首帧,所以草稿阶段只能验证提示词、节奏、字幕、配音、混音与渲染;
  视觉一致性只在成片档(H3)才成立。草稿通过不代表画面连贯。
- **即使上了 H3,车型外观目前也无法保证正确**:自动检索(`search_images` + 维基)
  拿到的是"大概率是这款车"的照片,校验层只剔被明确认出的别的车型;检索落空时还会退到 AI 编的
  参考图。画面里的车可能是"像汉的汉",不保证是那一台。要真正锁死外观,最可靠的做法是把真实照片放进
  `data/projects/<项目ID>/user_refs/` 后重跑素材层。

### 其他限制

- **`mcode-tools` 认证**:CLI 由 MiniMax Code 运行时注入,只能在 MiniMax Code 里用。
  在别处跑请用 direct 后端(M Plan 订阅 Key 直连),见「两种接口后端」。
- **direct 后端少两样**:同花顺 / 企查查的行情、财报、工商数据,以及配音的语音识别核对,
  只能经 MiniMax Code。品牌 / 市场方向的公司层事实会变少,靠网络搜索补。
- **H3 配额上限未知**:套餐确认含 H3,但具体额度与并发上限需从 MiniMax 控制台确认。
- **没有通用网络检索**:Connector 目录 176 个工具中不存在通用 `web_search`,
  也**不存在视频检索**工具。产品参数来自同花顺 `search_news` 的新闻语义检索(见下);
  真实视频片段靠自建抓取(见「真实素材与生成素材怎么混」)。
- **真实素材依赖本机网络**:B站 / Bing / 汽车之家 / 懂车帝国内直连;YouTube 需要
  `YTDLP_PROXY`;抖音多半需要 `YTDLP_COOKIES`。官网与官图库是网页解析,对方改版就可能
  失效(失效时安静降级,`clip_report.json` 里能看到原因)。命中率因车型而异,新车、
  小众车型的官方素材少 —— 先用 `tests/probe_media_search.py` 探一下。
- **平台视频常带台标 / 字幕**:质检只记警告不弃用,否则整条通路会空转。
- **`app/llm/minimax.py` 未经验证**:用户未提供订阅 Key,端点与模型名基于公开文档实现,
  未配置时自动回退 DeepSeek。⚠️ 一旦配置了 `MINIMAX_API_KEY`,`orchestrator._llm()`
  会**优先**用它,即切到这条未验证的路径;想继续用 DeepSeek 就别填这个 Key。
- **iFinD / 企查查**:企查查需要完整企业名或统一社会信用代码,简称会返回"未匹配"并
  自动降级。二者都**只覆盖公司与行业层面**,车型参数靠 `ifind.product_news` 补。
- **方向专属检索仍用新闻语义检索**:迭代史 / 真实成本 / 竞品参数这几类方向,
  现有新闻源未必稳定覆盖(保险、保养、保值率尤其难)。缓解手段是事实缺口横幅 +
  门禁 A 人工补充,而不是提高自动化率。若某方向长期拿不到事实,需单独立项接垂类数据源。
- **长视频墙钟**:240 秒(40 镜头)成片档约 90–180 分钟,墙钟与 180 秒相同(同为 2 波次)。
  草稿先行与分批审片是主要缓解手段。
- **`GEN_MAX_CONCURRENCY=8` 未经套餐验证**:与 MiniMax 控制台的实际并发上限不符时,
  墙钟估算会偏差;H3 的并发与额度上限仍需从控制台确认。
- **横屏输出**:架构上 `ratio` 已参数化,但首版只验证了 9:16。
