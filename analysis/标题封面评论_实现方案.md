# 实现方案:每条片 3 个标题 + 2 版封面 + 置顶评论

## Context
上一轮复盘指出:抖音/小红书的点击率 ≈ 封面 + 标题,评论互动是推荐的硬信号,而项目里这块最薄:
- 标题只有 `script_gen` 顺手产出的一个(8~16 字),发布时 `publish/metadata.py` 只做截断;
- 封面只出一版(`narration.make_cover`,横屏 1 张、竖屏 9:16 + 3:4 各 1 张);
- 没有任何评论区物料;发布记录不记录「用了哪个标题 / 哪版封面」,所以以后没法拿数据对照。

目标:成片后自动备好一套「包装」(3 标题 + 2 封面 + 1 条置顶评论 + 3 条备用回复),
发布抽屉里人工一键选,选择结果随发布记录落库,为"发 10 条后对照数据"留证据。

不做:自动在平台上发评论(抖音开放平台无此接口,小红书/视频号走浏览器自动化风险高、也容易被判营销号)——
只生成文案 + 一键复制,人去发。

## 方案

### 1. 新模块 `app/pipeline/packaging.py`(包装生成,一次 LLM 调用)
数据结构(pydantic,落盘 `projects/<id>/packaging.json`):
```
Packaging
  titles:  [TitleOption{text, kind, note}] × 3
  comment: PinnedComment{text, options:[A, B]}      # 置顶评论,二选一
  replies: [str] × 3                                # 预判争论的备用回复
  picked:  {title: 0..2, cover: "a"|"b"}            # 用户选择,默认 0 / "a"
  made_at, source: "llm" | "fallback"
```
**三个标题固定三种写法**(不是随便 3 个同义改写,否则没有可对照的维度):
1. `stake` 立场/反问型:「23 万的 YU7,买的是屏幕还是电池?」
2. `number` 数字+结论型:「YU7 标准版:15 分钟补 405 公里,够不够用」
3. `person` 人群/场景型:「预算 25 万、天天跑高速,选 YU7 哪个版本」

硬约束(全部在代码里校验,不信 LLM):
- **长度 ≤ 18 字**(小红书 20 字是最短平台上限,各平台共用同一批标题,冒号可拆两行以便封面复用);
- 数字只能来自事实层:标题里出现的数字必须能在 `facts.json`(未禁用)或 `script.json` 里找到,价格只用 `_price_of` 的结果;
- `forbidden_in()` 命中广告法/品类禁用词 → 该条丢弃重写;
- 禁用搜索词式标题:新增 profile 字段 `title_avoid`(「全面解析」「深度对比」「值不值得买」「一文看懂」),命中丢弃;
- 不得与脚本主论点 `thesis` 冲突(标题只能是 thesis 的另一种说法,不能引入新判断);
- 不足 3 条合格 → **确定性兜底**(纯函数模板,用 subject / 价格 / thesis 拼),保证永远出得来,`source="fallback"`。

**置顶评论**:
- 形式固定为「二选一」:A/B 两个选项,各 ≤ 8 字,总长 ≤ 40 字,带一个明确问题(「你会选标准版还是 GT?评论区投一票」);
- 选项来自本片真实的取舍点(主论点 thesis、`compare_with`、结论段的版本分歧),不是泛泛的「你怎么看」;
- 与片型结尾对齐:`pick_side` / `next_episode` 的片子,评论里的选项要和片尾提问一致(读 `project.variant.ending`);
- 同样过 `forbidden_in`;
- **备用回复 3 条**:预判最常见的争论(「车主 vs 黑」、价格、续航口径),每条只准引用有 fact id 的数字,
  不得出现未经事实层验证的缺点/优点(沿用「不许自己推测缺点」的底线)。

触发时机:
- `explainer.compose()` 结尾、封面生成之后,**best-effort**:失败只记日志,不影响成片(`try/except`,与 BGM 失败同级)。
- 已经 DONE 的旧项目:发布抽屉首次打开时懒生成(`GET /packaging` 发现没有 `packaging.json` 就生成)。
- 成本:一次 LLM 调用,约 ¥0.01 量级,计入 `costs.py`(estimate 沿用 LLM 的粗估价)。

### 2. 两版封面
思路:**A/B 的差别必须大到能测出点击率差异**,不是换个颜色。

| | 封面 A(现有,标题型) | 封面 B(钩子型,新增) |
|---|---|---|
| 版式 | 底部渐变 + 角标(车名·起售价)+ 标题 + 副标题(thesis) | 车图占大头,**一个超大数字或 ≤8 字钩子**压在上方/一侧,其余信息极简 |
| 文字来源 | 选中的标题(默认标题 1) | 标题 2(数字型)里抽出的那个核心数字/短语;抽不出就用 thesis 前 8 字 |
| 底图 | `library.cover_still` 第 1 名 | `cover_still(exclude=…)` 第 2 名(不同角度/同簇去重),没有第二张就同图换版式 |

实现:
- `narration.make_cover(..., layout="title" | "hook")`:`title` 走现有路径,**像素级不变**(回归基线);`hook` 新分支。
  竖屏 `_draw_portrait_cover` 同样加 `layout`,3:4 版同样重新排版而不是截取(沿用已有教训:截的话主文案会被挤出线外)。
- `library.cover_still(subject, exclude: Sequence[Path] = ())`:跳过已用的图和 dHash 近重复(复用 `near_dup_groups`)。
- 文件名:A 仍是 `cover.jpg` / `cover_vertical.jpg` / `cover_vertical_3x4.jpg`(不改,保证旧项目、`aspect.cover_path`、`maintenance.PROJECT_KEEP` 都不受影响);
  B 新增 `cover_b.jpg` / `cover_vertical_b.jpg` / `cover_vertical_3x4_b.jpg`,在 `aspect.py` 加 `cover_name_for(aspect, variant="a")`,`PROJECT_KEEP` 追加 B 的三个文件名。
- 视觉包:B 同样读 `looks.current().cover_accent`,保持每条片的视觉一致。
- 安全区:竖屏 B 的钩子大字避开顶部 / 右侧平台 UI 区(用 `aspect.portrait_grid` 里已有的安全区常量)。

### 3. 发布链路接入
- `publish/service.py`
  - `build_context()` 读 `packaging.json`,`ContentContext` 新增 `pinned_comment`、`title_options`(只作展示);
  - `enqueue()` 标题优先级:用户 override > `packaging.picked.title` > 原 `ctx.title`;仍然经过 `clamp_title` 和 `forbidden_hits`(发布前最后一道闸)。
  - `_cover_for()` 按 `picked.cover` 选 A/B 文件;小红书仍优先 3:4 版。
- `publications` 表加一列 `variant TEXT NOT NULL DEFAULT '{}'`(JSON:`{title_kind, title_idx, cover, comment}`),
  走 `db.py` 里现有的 `ALTER TABLE … ADD COLUMN` 迁移写法(`db.py:229` 起)。
- `metrics/store.py` 的 `analytics` 加 `by_title_kind` / `by_cover`(沿用 `by_aspect` 的 `_bucket` 聚合),
  样本不足 10 条时界面显示「样本太少,别下结论」。这是这套包装能"验证有没有用"的关键,不加就白做了。

### 4. API
- `GET  /api/projects/{id}/packaging`:返回 packaging(不存在则生成)。
- `POST /api/projects/{id}/packaging/regenerate`,body `{"what": "titles" | "comment" | "all"}`:重新生成;封面 B 重画走 `what: "cover"`。
- `PUT  /api/projects/{id}/packaging/pick`,body `{"title": 0..2, "cover": "a"|"b"}`。
- `GET  /api/projects/{id}/cover?variant=a|b`:`main.py:993` 现有端点加可选参数,默认 a(向后兼容)。
- `GET /publish/preview` 回传 `packaging`,前端一次拿全。

### 5. 前端(`pages/project.js` 的 `openPublish`,约 630 行起)
抽屉顶部新增「包装」区,在各平台卡片之上:
- 3 张标题卡(单选):显示写法标签(立场 / 数字 / 人群)、字数、本条能否过各平台长度;选中会同步写进各平台标题输入框(用户仍可手改)。
- 2 张封面缩略图(单选),点击放大;横屏 16:9,竖屏同时显示 9:16 与 3:4。
- 置顶评论:文本框 + 「复制」按钮;下面折叠 3 条备用回复,各带「复制」。
- 「重新生成」按钮(带 loading,沿用 `withLoading`)。
- 发布抽屉的"发布"提交时,把选择结果带进 `overrides`。

## 验证
- 单测(`pytest`):
  - 标题:超长丢弃、含未在事实里出现的数字丢弃、含「最强/第一」丢弃、全部不合格时走兜底且恰好 3 条;
  - 评论:二选一结构、≤40 字、禁用词;备用回复数字必须有 fact id;
  - 封面:`layout="title"` 输出与改动前**逐像素一致**(沿用 motion_regress 的思路建立基线);`hook` 版横屏/竖屏/3:4 三种尺寸都能出图且文件尺寸正确;
  - 迁移:旧库启动不报错,老发布记录 `variant` 读出 `{}`;
  - 发布:标题优先级(override > picked > 原标题);`picked.cover=b` 时 `_cover_for` 返回 B 文件;
  - **注意**:调 `orchestrator.create_project` 的测试一律用 `fresh_db` fixture(曾经漏过一行进正式库)。
- 手工:起 `aimovice-e2e`(8849 端口,不要动用户正在跑的 8848/8860),打开一个已 DONE 的项目 → 发布抽屉 →
  看到 3 标题 + 2 封面 + 评论 → 切换后各平台输入框跟着变 → 重新生成 → 发布到一个测试账号看 `publications.variant` 落了值。
- 看封面要用截图肉眼确认:钩子大字不压车、竖屏避开安全区、白底棚拍图用深色字。

## 风险与取舍
- **封面 B 的"钩子"如果抽不出数字**:退到 thesis 前 8 字;仍不行就只出 A,界面显示「只有 1 版封面」,不硬凑。
- **没有第二张干净官图**:同一底图换版式,A/B 差异变小;界面标注「同底图」,提醒别把差异归因到图。
- **LLM 编造数字**:靠"标题数字必须溯源到事实层"硬拦截,宁可落到兜底模板。
- **只有 10 条样本**:`by_title_kind` / `by_cover` 在样本少时只给趋势,不下结论——别用 3 条数据改标题策略。
- 范围控制:不改脚本生成流程、不动概念动画、不做自动发评论、不做 AB 流量分配(平台不支持同片多封面自动测试,靠不同条片对照)。
